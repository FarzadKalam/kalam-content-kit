# قرارداد فایل سفارش

`spec.json` با schemaVersion=1 ورودی مشترک است: kind، brand، references و دادهٔ اختصاصی مسیر. ساختار پایه در `contracts/content-spec.schema.json` است. زیرقراردادهای طراحی و ویدیو، payload اصلی Studio را حفظ می‌کنند؛ validator مستقل و pinشدهٔ Gateway مرجع دقیق قواعد است، نه schema قدیمی snapshot.

`dataRequests` نوع داده، مقصد request/شمارهٔ اسلاید/context، شهر یا رقابت، روز و فعال/ضروری‌بودن را تعیین می‌کند. گزینهٔ حذف‌شدهٔ city یا competition از فیلد همان فرم خوانده می‌شود. `dataEvidence` مسیر و hash مدرک، فیلدهای واقعاً اعمال‌شده و موارد دستیِ حفظ‌شده را ثبت می‌کند. schema این فیلدها داخل همین ریپو است؛ راهنمای رفتاری در public-data.fa.md.

`project.json` با schemaVersion=2 وضعیت سفارش، commit مبدأ، وضعیت تنظیمات زنده، مدرک ابزارهای واقعی جلسه، تأییدها و artifactها را نگه می‌دارد. سابقهٔ motion نسخهٔ اول نیز هنگام ساخت سفارش جامع حفظ می‌شود. فیلدهای اختصاصی موتور حذف نمی‌شوند.

`brief-N.json` دستور آماده برای اجرای عامل است. ساخت brief هیچ مدل تولیدی را اجرا نمی‌کند. مسیر تصویر برای هر اسلاید prompt، ابعاد، transparent و فایل‌های مرجع را برمی‌گرداند؛ متن قرارداد خروجی دارد و صوت fallback روشن. پرامپت ویدیو package همراه نام فایل‌های دقیق دارد. artifact به brief خودش مرتبط است؛ پس از تغییر spec باید brief تازه ساخته شود.

`assistantGuidance` در brief و خروجی `content guide <id>` شناخت همهٔ مسیرها، فرم فعال، ابزارهای ثبت‌شده و راهنمای پیشنهاد متناسب را منتقل می‌کند. دستورهای رفتاری از snapshot تنظیمات همان سفارش می‌آیند؛ برای سفارش قدیمی بدون این فایل، fallback صریح است و انتخاب‌های قبلی حفظ می‌شوند. در سفارش متن/صوت، `purpose: "motion"` یا `content new --purpose motion` نیاز به نریشن و سناریوی هماهنگ را منتقل می‌کند؛ مجوز تولید صدا نیست.

تنظیمات در زمان ساخت داخل پوشهٔ سفارش کپی می‌شوند. `content set --patch` شیء را ادغام و آرایه را کامل جایگزین می‌کند؛ قبل از تغییر نسخهٔ قبلی ذخیره و brief قبلی نامعتبر می‌شود. برای تعویض نوع یا برند، سفارش تازه بسازید. برای بازنویسی اسلایدها آرایهٔ کامل مطلوب را بدهید تا تغییر یک اسلاید تصادفاً اسلایدهای دیگر را حذف نکند.
